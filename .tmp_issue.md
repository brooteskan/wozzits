## Implementation schedule

Staged to preserve the current #140 path while moving toward the reflected/declarative model. Each phase builds on the previous; the existing manual `ports` path remains functional throughout.

### Architectural constraint: asset-only path must work without BehaviorRegistry

The current signatures show the constraint:

```cpp
// Asset layer — no BehaviorRegistry parameter
SceneAuthoringMaterializeReport materialize_scene_authoring_components(
    SceneAssetData& scene,
    EngineAssetLibrary& assets,
    const SceneAuthoringMaterializeOptions& options = {});

// Behavior layer — also no BehaviorRegistry parameter currently
bool build_kernel_library_from_scene(
    Device& device,
    const SceneAssetData& scene,
    const EngineAssetLibrary& assets,
    BehaviorGpuKernelLibrary& out_library,
    std::string* error = nullptr);
```

Both functions need port/binding data. Today they get it from scene-authored `ports`. The derived path must not require a behavior plugin to be loaded — `materialize_scene_authoring_components` lives in `engine/assets/scene/`, which must not depend on the behavior layer.

**Resolution: shader extraction is the primary source of truth for binding layout.** The HLSL file is always on disk (referenced by `hlsl_path`). Shader extraction provides everything needed for pipeline creation and runtime binding:

| Information needed | Source |
|---|---|
| Buffer binding kind (SRV/UAV) | `StructuredBuffer<T>` vs `RWStructuredBuffer<T>` |
| Shader register, register space | `register(t0)`, `register(u0, space1)` |
| Stride bytes | `sizeof(T)` from the structured buffer element type |
| Root constant offsets/dwords | cbuffer field order and types |
| Total `root_constant_dwords` | `max(offset + dwords)` across cbuffer fields |
| Port names | Shader identifiers, normalized |
| Port kind | Declaration type |
| Port direction | `StructuredBuffer` → input, `RWStructuredBuffer` → output, cbuffer → input |

The behavior contract is an **optional validation layer**: when a plugin registers a contract, the matcher checks that the behavior's expected ports are compatible with the shader's actual layout. Mismatches produce load-time diagnostics. But the pipeline and bindings work without it.

This makes Phase 1 (shader extraction) the foundation, not behavior contracts.

### Phase 1 — Shader-side binding extraction (lightweight prototype)

Parse register layout from HLSL source text. Not full DXC reflection — just enough for the structured-buffer + cbuffer scalar pattern used in the current kernels.

**Files (engine repo):**

- New `engine/assets/compute_pipeline/hlsl_binding_extract.h` / `.cpp` — Source-text parser that extracts:
  - `StructuredBuffer<T> Name : register(tN)` → SRV port, register N
  - `RWStructuredBuffer<T> Name : register(uN)` → UAV port, register N
  - `cbuffer Name : register(bN) { ... }` → root constant ports, one per scalar field, with derived dword offsets
  - Struct element type sizes for `stride_bytes`
  - Diagnostics for unsupported patterns (e.g., `Texture2D`, `AppendStructuredBuffer`, nested structs)

- Name normalization: shader identifiers are conventionally PascalCase (`Input`, `Factor`); behavior ports are snake_case (`input`, `factor`). The extractor normalizes to lowercase for matching. If this proves insufficient, add an annotation comment format (e.g., `// @port input`) as a follow-up.

**Design decision:** How to handle cbuffer field types beyond `uint` and `float`. For the prototype, support `uint` (→ `WZ_GPU_PORT_U32`), `float` (→ `WZ_GPU_PORT_F32`), and `uint2`/`float2`/`uint3`/`float3`/`uint4`/`float4` (→ multi-dword root constants). Flag anything else as a diagnostic.

**Acceptance:** `hlsl_binding_extract("shaders/compute/debug_multiply_u32_cs.hlsl")` returns four shader-side ports: `input` (SRV t0, stride 4), `output` (UAV u0, stride 4), `factor` (root constant, offset 0, 1 dword), `count` (root constant, offset 1, 1 dword).

### Phase 2 — Behavior-side kernel contract declaration

Add a registration path for behavior plugins to declare GPU kernel contracts at load time. This is the optional validation layer — not required for pipeline creation, but enables load-time mismatch diagnostics.

**Files (engine repo):**

- `behavior_plugin_abi.h` — New ABI structs (bumps ABI version):
  ```c
  typedef struct WzGpuKernelPortContractDesc {
      const char* name;
      WzGpuPortKind kind;       // WZ_GPU_PORT_STRUCTURED_BUFFER / U32 / F32
      WzGpuPortDirection direction;
      uint32_t stride_bytes;    // structured buffer only
  } WzGpuKernelPortContractDesc;

  typedef struct WzGpuKernelContractDesc {
      const char* kernel_id;
      const WzGpuKernelPortContractDesc* ports;
      uint32_t port_count;
  } WzGpuKernelContractDesc;
  ```
  New function pointer typedef `WzRegisterGpuKernelContractFn`. Add `register_gpu_kernel_contract` to `WzBehaviorPluginApi` alongside the existing `register_behavior` / `register_module` / `register_module_desc` pointers.

- `behavior_module_api.h` — C/C++ helper macros that build a `WzGpuKernelContractDesc` and call `api->register_gpu_kernel_contract`:
  ```c
  WZ_GPU_KERNEL(var, kernel_id_string)
  WZ_GPU_STRUCTURED_INPUT(name, element_type)
  WZ_GPU_STRUCTURED_OUTPUT(name, element_type)
  WZ_GPU_U32(name)
  WZ_GPU_F32(name)
  WZ_GPU_KERNEL_END(var)          // calls register
  ```
  The macro set builds a static port array and submits it during `wz_register_behaviors`.

- `behavior_registry.h` — New `BehaviorGpuKernelContract` struct (engine-owned, owning strings). New storage and accessor on `BehaviorRegistry`, e.g. `register_gpu_kernel_contract()` / `gpu_kernel_contracts()`.

- `behavior_plugin_adapter.cpp` — Wire `WzBehaviorPluginApi::register_gpu_kernel_contract` to `BehaviorRegistry::register_gpu_kernel_contract()`.

- `sample_behavior_plugin.cpp` (`mesh_trials/behavior/`) — The `gpu_trial` module declares the `debug/multiply_u32` contract:
  ```c
  WZ_GPU_KERNEL(multiply_kernel, "debug/multiply_u32")
      WZ_GPU_STRUCTURED_INPUT("input", uint32_t)
      WZ_GPU_STRUCTURED_OUTPUT("output", uint32_t)
      WZ_GPU_U32("factor")
      WZ_GPU_U32("count")
  WZ_GPU_KERNEL_END(multiply_kernel)
  ```

**Acceptance:** After loading the `gpu_trial` module, `BehaviorRegistry::gpu_kernel_contracts()` returns one entry for `debug/multiply_u32` with four ports. No runtime dispatch changes yet.

### Phase 3 — Contract matching and binding derivation

Build the central matcher that derives runtime bindings from shader extraction, optionally validated against a behavior contract.

**Files (engine repo):**

- New `engine/behavior/behavior_gpu_kernel_contract_match.h` / `.cpp`:
  - Shader-only path (always works, no behavior dependency):
    ```cpp
    DerivedKernelBindings derive_kernel_bindings(
        const ShaderBindingExtraction& shader);
    ```
  - Validated path (with optional behavior contract):
    ```cpp
    DerivedKernelBindings derive_kernel_bindings(
        const ShaderBindingExtraction& shader,
        const BehaviorGpuKernelContract* behavior_contract,  // nullable
        std::vector<KernelContractDiagnostic>& diagnostics);
    ```
  - Match ports by normalized name when both sources are available.
  - Validate: kind compatibility (behavior `STRUCTURED_BUFFER` ↔ shader SRV/UAV), direction compatibility (behavior `INPUT` ↔ shader SRV; behavior `OUTPUT` ↔ shader UAV).
  - Derive `BehaviorGpuKernelPortBinding` per port: target (BufferBinding vs RootConstant), binding_kind, shader_register, register_space, root_constant_offset, root_constant_dwords.
  - Derive total `root_constant_dwords` as `max(offset + dwords)` across root constant ports.
  - Structured diagnostics: missing ports (behavior expects X, shader doesn't have it), extra ports (shader has X, behavior doesn't reference it — warning, not error), kind mismatches, direction mismatches, duplicate names.

- `behavior_gpu_compute_executor.cpp` — Extend `build_kernel_library_from_scene()` (or add a parallel path) to accept derived bindings instead of scene-authored `ports` when the scene component has no `ports` array. When `BehaviorRegistry` is available, pass contracts for validation; when not, use shader-only derivation.

**Acceptance:** `build_kernel_library_from_scene()` can build `debug/multiply_u32` using shader extraction alone (no behavior contract, no scene-authored `ports`). The executor dispatches and readback produces the same results as the existing manual-port test. When a behavior contract is also available, mismatch diagnostics are produced.

### Phase 4 — Scene component migration

Make `ports` optional in the scene `compute_kernel` component. Both paths coexist.

**Files (engine repo):**

- `scene_compilers.cpp` — Parser accepts `compute_kernel` without `ports`. Missing `ports` is not an error.
- `scene_json_export.cpp` — Export omits `ports` when the component was loaded without them.
- `scene_fingerprint.cpp` — When `ports` is absent, fingerprint mixes only the kernel reference fields (kernel_id, hlsl_path, entry, target, thread_group_size). No port fields in the hash.
- `scene_authoring_materialize.cpp` — Materialization branches: if `ports` present, use the current #140 path; if absent, run shader extraction on `hlsl_path` and call `derive_kernel_bindings(shader)` to build pipeline bindings. This stays in the asset layer — no `BehaviorRegistry` dependency.
- Tests: add migration tests covering both old (manual ports) and new (derived) scene JSON for the same kernel, verifying both produce identical pipeline data.

**Acceptance:** This minimal scene JSON materializes and resolves to a working pipeline:
```json
"compute_kernel": {
  "kernel_id": "debug/multiply_u32",
  "hlsl_path": "shaders/compute/debug_multiply_u32_cs.hlsl",
  "entry": "main",
  "target": "cs_5_0",
  "thread_group_size": [4, 1, 1]
}
```

### Phase 5 — Editor UI rework

Replace the editable port table with read-only contract discovery.

**Files (wozzits-imgui, scene editor toolhost):**

- `scene_editor_components_editor_core.inc` — Remove the manual port table and "Add Buffer Port" / "Add Constant" buttons. Inspector shows only editable kernel reference fields (kernel_id, hlsl_path, entry, target, thread_group_size).
- Add a read-only "Discovered Ports" section below the kernel fields: a table showing each extracted port (name, kind, direction, register/offset), with color-coded rows for mismatches when a behavior contract is available.
- `scene_editor_panels_component_browser.cpp` — `attach_compute_kernel()` default template drops the ports array. The template becomes just kernel_id + hlsl_path + entry + target + thread_group_size.
- `scene_editor_components_helpers_common.inc` — The `compute_kernel_port_kind_index` / `_from_index` / `_direction` / `_binding_kind` helpers become read-only display helpers or are removed.

**Acceptance:** User can author `debug/multiply_u32` in the editor without typing port names, registers, or stride bytes. The discovered ports appear read-only.

### Phase 6 — Runtime and toolhost integration

Use the derived path in both the game loop and the scene editor preview.

**Files (both repos):**

- `game_app.cpp` — When a scene-load-from-JSON path exists, `build_kernel_library_from_scene()` uses the derived path for nodes without manual ports. If `BehaviorRegistry` is populated (plugins loaded), pass contracts for validation diagnostics.
- Scene editor toolhost — Behavior frame dispatch uses the derived kernel library. Contract resolution errors surface in the status panel.
- Ensure scene reload / re-materialization refreshes extracted bindings and kernel libraries.

**Acceptance:** The `gpu_trial` module's `debug/multiply_u32` job dispatches through derived bindings in both game_app and editor preview.

---

### Phase 7 — Cleanup and sample migration

Move samples fully onto the derived model.

**Files (engine repo):**

- Remove `ports` from `mesh_trials` scene JSON.
- Update #140 tests to assert the derived path as the preferred path.
- Add adversarial mismatch tests: behavior expects port shader doesn't have (error), shader has extra port behavior doesn't use (warning), kind mismatch (error), direction mismatch (error).
- Decide whether to keep the manual `ports` fallback for edge cases or remove it entirely. If removed, delete `SceneComputeKernelPortAsset` and all port parsing/export/fingerprint code from #140 Phases 1-4.

**Acceptance:** No production sample manually authors compute kernel ports. The `ports` fallback is either documented as an escape hatch or removed.

### Dependency chain

```
Phase 1 (shader extraction) ──→ Phase 3 (matching/derivation) → Phase 4 (scene migration, engine)
Phase 2 (behavior contracts) ─↗                                      ↓
                                                                Phase 5 (editor UI, wozzits-imgui)
                                                                      ↓
                                                                Phase 6 (runtime integration, both repos)
                                                                      ↓
                                                                Phase 7 (cleanup)
```

Phases 1 and 2 are independent. Phase 3 requires Phase 1; Phase 2 is optional input to Phase 3. Suggested build order: Phases 1–4 in the engine repo first, then Phase 5 in wozzits-imgui. This avoids building editor UI on an unstable contract data model.

### Design decisions to resolve early

1. **Contract registration scope.** Should `register_gpu_kernel_contract` be a standalone call on `WzBehaviorPluginApi`, or an optional field on `WzBehaviorModuleDesc`? Standalone is more flexible (a plugin could register contracts without being a module), but module-scoped ties contracts to the module lifecycle. The plan assumes standalone.

2. **Name normalization.** The prototype uses case-insensitive lowercase matching (shader `Input` ↔ behavior `input`). If this proves ambiguous, annotation comments (`// @port input`) are the fallback. Decide before Phase 3.

3. **Manual `ports` end-of-life.** Phase 4 keeps the manual path as a fallback. Phase 7 must decide: keep it as a documented escape hatch (for shaders the extractor can't parse), or remove it. This affects how much #140 code survives.
