## Phased Plan

### Phase 1 — Scene data and JSON round-trip

Add the `compute_kernel` component to the scene data layer. No editor UI, no materialization, no runtime. Just the data structures and serialization.

**Files:**

- `scene_asset_data.h` — Add `SceneComputeKernelPortAsset` struct (name, kind, direction, binding_kind, shader_register, register_space, stride_bytes, root_constant_offset, root_constant_dwords). Add `SceneComputeKernelAsset` struct (kernel_id, hlsl_path, entry, target, thread_group_size x/y/z, ports vector). Add `std::optional<SceneComputeKernelAsset> compute_kernel` to `SceneNodeAsset`.
- `scene_ecs.h` — Add `ComputeKernel` to `SceneAuthoredComponentKind` enum. Add counter to summary struct. Classify under `SceneComponentDomain::Exportable` (kernels must survive asset export, per the architectural principle that a game should be buildable from the asset export alone).
- `scene_compilers.cpp` — JSON parsing for `"compute_kernel"` object: kernel_id, hlsl_path, entry, target, thread_group_size, ports array. Each port: name, kind (structured_buffer / u32 / f32), direction (input / output), and conditional fields — for buffer: binding_kind (srv / uav), shader_register, register_space, stride_bytes; for root constant: offset, dword_count.
- `scene_json_export.cpp` — Export `compute_kernel` back to JSON.
- `scene_fingerprint.cpp` — Mix kernel_id, hlsl_path, entry, target, thread_group_size, and all port fields into fingerprint.
- `scene_authoring_component_roundtrip_tests.cpp` — Round-trip test: construct a node with `compute_kernel`, export to JSON, re-import, verify all fields match.

**Acceptance:** A `compute_kernel` component can be authored in JSON, parsed, exported, and round-tripped with fidelity. No runtime effect yet.

### Phase 2 — Asset materialization

Wire the scene `compute_kernel` component into the asset graph so it produces real shader and compute pipeline assets.

**Files:**

- `scene_authoring_materialize.cpp` — In materialization, when a node has `compute_kernel`: call `assets.shaders().create_compute_shader()` with the HLSL path/entry/target, then `assets.compute_pipelines().create_compute_pipeline()` with the shader, bindings derived from ports, thread group size, and root_constant_dwords (derived from max port offset + dwords across root constant ports). The pipeline asset is registered but not yet consumed by the behavior system.
- Materialization test: materialize a scene with a compute_kernel component, verify the pipeline data exists in the `ComputePipelineTable` with correct bindings, thread group size, and root constant count.

**Acceptance:** Loading a scene with a `compute_kernel` component creates shader and pipeline assets in the asset graph. `assets.resolve_all()` compiles the shader and pipeline successfully.

---

### Phase 3 — Kernel library and executor wiring

Build the runtime `BehaviorGpuKernelLibrary` from resolved scene compute kernel components, wire it into the game loop, and route completion/failure events back to behaviors.

**Files:**

- `behavior_gpu_compute_executor.h` — Add `BehaviorGpuKernelLibrary` struct: a vector of `BehaviorGpuKernelBinding` entries plus a lookup method by kernel name.
- New function (in executor or a new `behavior_gpu_kernel_library.cpp`) — `build_kernel_library_from_scene()`: iterates scene nodes with `compute_kernel`, looks up the resolved `ComputePipelineData` and creates the GPU pipeline handle via `create_compute_pipeline()`, maps each scene port to a `BehaviorGpuKernelPortBinding`, and inserts into the library.
- `game_app.cpp` — After scene load/resolve, call `build_kernel_library_from_scene()` and store the library. After `dispatch_behaviors()` collects jobs, call `dispatch_behavior_gpu_compute_jobs(device, jobs, library)`. Convert the dispatch report into completion/failure events via `BehaviorGpuComputeBuffer::add_event()` for the next frame's dispatch. Clear events after dispatch.
- End-to-end test: scene JSON with compute_kernel component → materialize → resolve → build library → submit job from test behavior → executor dispatches → readback matches expected output → completion event routes back.

**Acceptance:** A behavior plugin calling `wz_gpu_begin(&job, "project/debug_multiply_u32")` resolves through the kernel library to the GPU pipeline built from the scene-authored compute kernel component. Completion/failure events are routed to the submitting behavior.

### Phase 4 — Editor UI

Add the component to the scene editor so users can add and configure compute kernels without editing JSON.

**Files:**

- Scene editor component panel (wherever collision, terrain, behavior, mesh_wavelet_analysis components are rendered) — Add "Compute Kernel" to the add-component menu. UI fields: kernel_id text input, hlsl_path file picker (project-relative), entry text input (default "main"), target dropdown (default "cs_5_0"), thread group size x/y/z spinners.
- Port table with add/remove: each row has name text, kind dropdown (Structured Buffer / U32 / F32), direction dropdown (Input / Output). Conditional detail fields appear based on kind — for buffer: binding kind (SRV/UAV), shader register, register space, stride bytes; for root constant: offset, dword count.
- The component should trigger re-materialization on edit, like other scene components.

**Acceptance:** User can add a Compute Kernel component in the editor, fill in all fields, and the authored data round-trips through JSON and materializes into working GPU pipeline assets. The `debug/multiply_u32` sample kernel can be authored entirely through the UI.

Remove or replace the hardcoded debug kernel path. Author the sample kernel through a scene component.

**Files:**

### Design decisions to resolve early

1. **Root constant dword count derivation.** The `ComputePipelineDesc` needs a total `root_constant_dwords`. This should be *derived* from the port contract: `max(offset + dwords)` across all root constant ports. No separate user-facing field — one fewer thing to get wrong.

2. **Port target discrimination.** `BehaviorGpuKernelPortBinding` has fields that only apply to specific targets (buffer ports use `binding_kind`/`shader_register`; root constant ports use `offset`/`dwords`). The scene data struct should mirror this with clear comments or separate sub-structs, so JSON parsing can validate that buffer-only fields aren't set on root constant ports and vice versa.

3. **Kernel library rebuild.** When the editor re-saves a scene (adding/editing a compute kernel), the kernel library must be rebuilt. This should happen through the existing scene reload/re-materialize path — the library is derived from the resolved asset graph, so it rebuilds whenever the graph resolves.

4. **Multiple compute_kernel components.** A single scene node probably shouldn't host multiple compute kernels (use separate nodes, e.g. a "Kernels" node with children). But the scene *as a whole* should support many compute_kernel components across different nodes, each registering a different kernel_id. The library aggregates all of them. Duplicate kernel_ids across nodes should be flagged as an error.
