## Problem

Compute kernels have a scene-authored component (`SceneComputeKernelAsset`) that declares HLSL shaders and bindings in scene JSON, with materialization into GPU pipeline assets. The render side has no equivalent — custom render programs can only be created through the `BuiltinRenderProgram` enum in C++. There is no path for scene authors or the editor to declare custom vertex/pixel shaders with explicit pipeline state.

## Desired architecture

Mirror the compute kernel pattern for render programs:

```json
"render_shader": {
  "program_id": "mesh/custom_surface",
  "vertex_hlsl_path": "shaders/render/custom_mesh_vs.hlsl",
  "pixel_hlsl_path": "shaders/render/custom_mesh_ps.hlsl",
  "vertex_entry": "main",
  "pixel_entry": "main",
  "vertex_target": "vs_5_0",
  "pixel_target": "ps_5_0",
  "binding_model": "mesh_ia",
  "input_layout": "mesh_position_normal_uv",
  "blend": "opaque",
  "depth": "test_write",
  "raster": "solid_cull_none"
}
```

Materialization creates:
1. Shader pair (`ShaderAssetModule::create_shader_pair`)
2. Custom render program asset (`RenderProgramAssetModule::create_custom`)
3. Assigns the resulting render program to the node's renderable

## Existing infrastructure

- `RenderProgramData` already holds the full declarative PSO layout (input layout, blend, depth, raster, root constants, descriptor bindings, shader handles).
- `RenderProgramPipelineCache` realizes `RenderProgramData` into DX12 graphics pipelines.
- The submit path already prefers `render_program` when `RenderableAssetData::render_program` is valid.
- `RenderProgramAssetModule` has `create_builtin(...)` that accepts `BuiltinRenderProgramDesc`. A second entry point (`create_custom(...)`) is needed that accepts fully-authored `RenderProgramData` fields directly instead of deriving them from a `BuiltinRenderProgram` enum.

## Scope — first milestone

Support custom mesh surface shaders only:
- `binding_model = MeshIA`
- `input_layout = MeshPositionNormalUV`
- Root constants matching existing mesh surface layout
- Optional `MeshFieldVisualization` descriptor (added later)

Avoid at first:
- Arbitrary descriptor semantics
- Custom textures/samplers
- Splat/terrain/fullscreen binding models
- Shader reflection for render programs

## Acceptance criteria

1. A scene JSON with `render_shader` on a mesh node produces a working custom render program that the submit path uses instead of the builtin.
2. The render program roundtrips through JSON export/import without loss.
3. The existing builtin render program path is unchanged.
4. A test verifies the full round trip: JSON -> parse -> materialize -> compile -> verify `RenderProgramData` fields match the authored values.

## Implementation phases

1. **Custom render program desc + compiler** — `CustomRenderProgramDesc`, `create_custom(...)`, new `kCustomRenderProgramSchema`, compiler that maps authored fields directly to `RenderProgramData`.
2. **Scene component + JSON round trip** — `SceneRenderShaderAsset` on scene nodes, JSON parsing/export, classification as authoring recipe.
3. **Materialization** — `materialize_render_shader()` creates shader pair + custom render program, wires the render program key into the renderable.
4. **End-to-end visual verification** — test HLSL shader pair, test scene, confirm rendering.

## Notes

This follows the pattern established by `SceneComputeKernelAsset` in #136. The compute kernel path has a good precedent, and rendering already has half of the infrastructure.
