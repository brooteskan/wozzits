## Implementation schedule

Staged to eliminate the CPU readback/re-upload roundtrip for large wavelet field outputs while preserving disk caching and existing small-field paths. Each phase is independently testable. The existing CPU-readback path remains functional throughout as a fallback.

### Current bottleneck

The wavelet GPU compiler (`compile_wavelet_gpu_detail_heat`) dispatches compute on the GPU, then:

1. **Reads back** the entire output buffer to CPU (`readback_buffer`) -- 224MB for 8M vertices x 7 channels
2. Parses the readback bytes into `MeshDerivedFieldData` (CPU-owned `std::vector<std::byte>`)
3. Stores the CPU data in `MeshDerivedFieldTable` and optionally disk-caches it
4. Later, the render resource resolver **re-uploads** one channel to GPU (`upload_mesh_field_visualization`) -- 32MB per channel

The data round-trips through CPU memory unnecessarily. For the rendering path, the data was already on the GPU after step 1.

### Architectural constraint: compiler layer owns GPU compute, render layer owns visualization

The wavelet compiler runs during `resolve_all()` in the asset layer. The render resource resolver runs during `prepare()` in the rendering layer. They share no direct state. The bridge is `MeshDerivedFieldData` in the `MeshDerivedFieldTable` -- the compiler produces it, the render resolver consumes it.

For GPU-resident fields, we need a new bridge: per-channel GPU handles produced by the compiler, consumed by the render resolver without re-upload.

### Phase 1 -- GPU sub-region copy and GPU-resident field table

Add the GPU-layer primitive for creating a mesh field visualization resource from a byte region of an existing GPU buffer (GPU-to-GPU copy, no CPU involvement). Add a table for the asset layer to store per-channel GPU handles that the render layer can discover.

**Files (engine repo):**

- `gpu/mesh_field_visualization.h` -- New function:
  ```cpp
  GPUHandle create_mesh_field_visualization_from_gpu_source(
      Device& device,
      GPUHandle source_buffer,
      uint64_t byte_offset,
      uint32_t element_count,
      uint32_t stride_bytes);
  ```
  Creates a new DEFAULT-heap buffer, copies `element_count * stride_bytes` from `source_buffer` at `byte_offset` via `CopyBufferRegion`, creates a structured SRV over the new buffer, and registers it in the existing `DX12MeshFieldVisualizationTable`. Returns a `GPUHandle` usable as a `mesh_field_visualization_resource` by the render path.

- `src/gpu/dx12/dx12_mesh_field_visualization.cpp` -- Implementation: allocate command list, transition source to COPY_SOURCE, create destination DEFAULT buffer, `CopyBufferRegion`, create SRV, execute and wait, register in table.

- `engine/assets/mesh_derived_field/mesh_derived_field.h` -- New `GpuResidentFieldEntry` struct:
  ```cpp
  struct GpuResidentFieldEntry
  {
      wz::asset::AssetKey field_key{};
      uint32_t channel_id = 0;
      wz::gpu::GPUHandle gpu_resource{};
  };
  ```
  New `GpuResidentFieldTable` class with `add()`, `find(AssetKey, channel_id)`, `clear()`, `destroy(Device&)`. Stored in `EngineAssetLibrary` alongside `MeshDerivedFieldTable`.

- `engine/assets/engine_asset_library.h` -- Add `GpuResidentFieldTable& gpu_resident_fields()` accessor.

- Test: create a structured buffer with known float data, call `create_mesh_field_visualization_from_gpu_source` to extract a sub-region, verify the returned handle is valid.

**Acceptance:** `create_mesh_field_visualization_from_gpu_source` produces a valid visualization resource from a byte offset of an existing GPU buffer. `GpuResidentFieldTable` stores and retrieves entries by asset key + channel ID.

### Phase 2 -- Render resource resolver consumes GPU-resident fields

Wire the render resource resolver and GPU cache to check for GPU-resident field resources before falling through to the CPU upload path.

**Files (engine repo):**

- `src/engine/rendering/renderable_gpu_cache.cpp` -- In `prepare()`, after finding the cached mesh but before calling `upload_mesh_field_visualization`, check `GpuResidentFieldTable::find(field_asset, channel_id)`. If a GPU handle exists, use it directly as `mesh_field_visualization_resource`. Skip the `get_mesh_derived_field_data` / upload path.

- `src/engine/rendering/gpu_scene_render_resource_resolver.cpp` -- Same check in the preview path: before resolving `MeshDerivedFieldData` from the table, check the GPU-resident field table. If found, use the GPU handle directly.

- `engine/rendering/renderable_gpu_cache.h` -- `prepare()` signature adds `const GpuResidentFieldTable&` parameter (or receives it through the existing `EngineAssetLibrary&`).

- Test: manually populate a `GpuResidentFieldEntry` for a known field asset + channel, call `prepare()`, verify it uses the GPU-resident handle and does NOT call `upload_mesh_field_visualization`.

**Acceptance:** When a GPU-resident field entry exists for the requested field + channel, the render resolver uses it directly. When no entry exists, the existing CPU upload path runs as before.

### Phase 3 -- Wavelet GPU compiler retains compute output and produces GPU-resident channels

Modify the wavelet GPU compiler to keep the compute output buffer after dispatch and use Phase 1's API to extract per-channel visualization resources. Skip the CPU readback for the rendering path.

**Files (engine repo):**

- `src/engine/assets/mesh_derived_field/mesh_derived_field_compilers.cpp` -- In `compile_wavelet_gpu_detail_heat`:
  - After `dispatch_compute` succeeds, do NOT call `readback_buffer` yet.
  - For each channel (position energy per scale, normal energy per scale, detail cost), compute the byte offset into the output buffer and call `create_mesh_field_visualization_from_gpu_source` to create a per-channel GPU resource.
  - Register each GPU resource in the `GpuResidentFieldTable` with the field's asset key and channel ID.
  - Release the full compute output buffer after all channels are extracted.
  - Produce a `MeshDerivedFieldData` with channel metadata (channel_id, value_type, byte_offset, byte_count, element_count) but empty `values` vector.
  - Do NOT release the input buffer -- that's still released immediately (it's only needed for compute).

- `src/engine/assets/mesh_derived_field/mesh_derived_field.cpp` -- Relax `MeshDerivedFieldData::valid()`:
  - Add a `bool gpu_resident = false` flag to `MeshDerivedFieldData`.
  - When `gpu_resident` is true, validation checks channel metadata integrity but does not require `values.size() == expected_total`. The CPU values may be empty.
  - When `gpu_resident` is false, existing validation is unchanged.

- `engine/assets/mesh_derived_field/mesh_derived_field_compilers.h` -- `register_mesh_derived_field_compilers` gains a `GpuResidentFieldTable&` parameter.

- `src/engine/assets/engine_asset_library_compiler_registry.cpp` -- Pass the GPU-resident field table to the wavelet compiler registration.

- Existing disk cache path: `store_cached_mesh_derived_field` is skipped when `values` is empty (GPU-resident fields have no CPU data to cache at this point -- Phase 4 addresses this).

**Acceptance:** For a mesh with `N` wavelet channels, the compiler produces `N` GPU-resident field entries and a `MeshDerivedFieldData` with `gpu_resident = true` and empty `values`. The render resource resolver (from Phase 2) finds the GPU-resident entries and renders the field visualization without any CPU readback or re-upload. The CPU reference fallback path is unchanged.

### Phase 4 -- Deferred readback for disk caching

After GPU compute produces a GPU-resident field, perform a deferred readback to populate the CPU values for disk serialization. This is a one-time cost that enables cache hits on reload, avoiding recomputation.

**Files (engine repo):**

- `src/engine/assets/mesh_derived_field/mesh_derived_field_compilers.cpp` -- In `compile_wavelet_gpu_detail_heat`, after extracting per-channel GPU resources:
  - Call `readback_buffer` on the full compute output buffer (before releasing it) to get the CPU bytes.
  - Parse the readback bytes into the `MeshDerivedFieldData::values` vector and set `gpu_resident = false` (the field now has both GPU and CPU representations).
  - Call `store_cached_mesh_derived_field` to write the disk cache.
  - This means the readback still happens, but it's decoupled from the rendering path -- the render path already has GPU handles from Phase 3 and doesn't need to wait for or use the readback data.

- Future optimization (not this phase): make the readback truly asynchronous using a fence-based callback or deferred frame. For now, synchronous readback is acceptable because it only blocks asset resolution, not rendering.

**Design note:** The readback in Phase 4 means the total GPU memory savings come from eliminating the re-upload, not the readback. The readback is still needed for disk caching. The performance win is:
  - Before: readback (224MB) + later re-upload (32MB per channel) = CPU roundtrip on the rendering critical path
  - After: readback (224MB, during resolve_all, not on render path) + GPU-to-GPU copy (32MB per channel, fast) = no CPU data on the render path

**Acceptance:** Disk cache is populated for GPU-computed wavelet fields. On reload, cache hit loads from disk and the existing CPU upload path works. The render path uses GPU-resident handles and never re-uploads from CPU data for GPU-computed fields.

### Phase 5 -- Behavior wavelet summary events

Add a small event type for wavelet analysis completion so behaviors can observe results without receiving the large field data.

**Files (engine repo):**

- `engine/behavior/behavior_plugin_abi.h` -- New event kind `WZ_EVENT_WAVELET_ANALYSIS_COMPLETED`. New event payload struct:
  ```c
  typedef struct WzWaveletAnalysisCompletedPayload
  {
      uint32_t element_count;
      uint32_t channel_count;
      uint32_t scale_count;
      uint8_t  gpu_resident;
  } WzWaveletAnalysisCompletedPayload;
  ```

- `engine/behavior/behavior_gpu_compute.h` -- Helper to construct wavelet completion events.

- `src/engine/assets/mesh_derived_field/mesh_derived_field_compilers.cpp` -- After successful wavelet compilation (GPU or reference), post a completion event if a behavior event channel is available.

- `src/engine/game_app.cpp` -- Route wavelet completion events to behavior modules via the existing event dispatch path.

**Acceptance:** After wavelet analysis resolves, the `gpu_trial` module receives a `WZ_EVENT_WAVELET_ANALYSIS_COMPLETED` event with element_count, channel_count, and scale_count. No field data bytes are in the event payload.

### Dependency chain

```
Phase 1 (GPU copy API + field table) --> Phase 2 (render resolver integration)
                                     --> Phase 3 (wavelet compiler retains output)
                                                      |
                                              Phase 4 (deferred readback for disk cache)
                                              Phase 5 (behavior events)
```

Phases 1 is the foundation. Phases 2 and 3 both depend on Phase 1 and can be built in either order, but 3 needs 2 wired up to verify end-to-end. Phases 4 and 5 are independent of each other and can proceed in parallel after Phase 3.

---

### Design decisions to resolve early

1. **GPU-resident field table ownership.** The plan places `GpuResidentFieldTable` in `EngineAssetLibrary` so both the compiler (asset layer) and render resolver (rendering layer) can access it. Alternative: put it in a shared `GpuFieldCache` that both layers receive by reference. The plan assumes `EngineAssetLibrary` since the render resolver already receives it.

2. **Compute output buffer lifetime.** Phase 3 extracts per-channel resources then releases the full output buffer. Alternative: keep the full output buffer alive and create SRVs as sub-views (no copy). This saves GPU memory for the copy but requires the output buffer to stay alive for the entire field lifetime. D3D12 supports sub-buffer SRVs natively. The per-channel copy approach is simpler (each channel is a standalone resource with independent lifetime) but uses ~2x GPU memory during extraction. For 8M vertices, the full output is ~224MB and each channel copy is ~32MB. The copy approach is simpler and the memory is transient (full buffer released after extraction).

3. **`MeshDerivedFieldData::valid()` relaxation.** Adding `gpu_resident` as a boolean flag is the simplest approach. Alternative: split into `MeshDerivedFieldData` (always has CPU values) and `GpuResidentMeshDerivedFieldData` (channel metadata only). The flag approach avoids splitting the type system and is used only in the compiler and render resolver.

4. **Deferred vs synchronous readback.** Phase 4 uses synchronous readback during `resolve_all()`. This is acceptable because `resolve_all()` already blocks on GPU compute (the wavelet dispatch itself is synchronous). True async readback (fence-based, multi-frame) is a future optimization that requires a different asset resolution model. The win from this plan is eliminating the re-upload on the render path, not eliminating the readback entirely.

5. **Scope of GPU-resident optimization.** This plan targets the wavelet GPU compiler specifically. The explicit field path (`pack_explicit_field`) and the CPU reference wavelet path (`compile_wavelet_reference`) continue to produce CPU-owned field data. Extending GPU residency to other field types is a future concern.
